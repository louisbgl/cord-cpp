# CLAUDE.md

Behavioral guidelines for working on cord. Read before coding.

## 1. Think Before Coding

Before implementing:
- State assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

Minimum code that solves the problem. Nothing speculative.

- No features beyond what was asked.
- No abstractions for single-use code.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

## 3. Surgical Changes

Touch only what you must. Clean up only your own mess.

- Don't "improve" adjacent code, comments, or formatting unprompted.
- Don't refactor things that aren't broken.
- Match existing style. C++ methods in .cpp follow .hpp declaration order.
- If you notice unrelated dead code, mention it — don't delete it.
- Remove imports/variables/functions that YOUR changes made unused.

## 4. Goal-Driven Execution

Transform tasks into verifiable goals. For multi-step tasks, state a brief plan first and verify each step.

"Fix the bug" → write a test that reproduces it, then make it pass.
"Add feature" → confirm it fits the flat key-value design, then implement.

## Project: cord

Header-only C++20 config parser. Flat key-value only — no nesting, no sections, intentionally.

### Architecture

Single public header `cord.hpp` (generated). Source of truth is `src/`:
- `common.hpp` — type traits, supported type list, error macro
- `exception.hpp` — `CordException`
- `errors.hpp` — `ParseError`, `ErrorCollector`
- `field.hpp` — `FieldType`, `Value`, `IField`, `Field<T>`
- `schema.hpp` — `Result`, `Schema` (main workhorse)
- `cord.hpp` — re-exports all of the above

`cord.hpp` at root is generated by `scripts/gen_single_header.py`. Run it after touching `src/`. CI tests both `src/` and the generated header.

### Build & Test

```bash
cmake -S . -B build && cmake --build build
ctest --test-dir build --output-on-failure

# Examples
cmake --build build --target run_simplest
cmake --build build --target run_arrays
cmake --build build --target run_optionals
cmake --build build --target run_config_markers
cmake --build build --target run_constraints

```

### Pre-merge Checklist

Before pushing or merging a feature branch:

- [ ] All tests pass: `ctest --test-dir build --output-on-failure`
- [ ] All examples run: `cmake --build build --target run_<example>` for each
- [ ] New public template API has a compile-fail test in `tests/compile_fail/`
- [ ] Tests added for new behavior (happy path + edge cases)
- [ ] Regression test added if fixing a bug
- [ ] README updated: features list, API reference, examples list
- [ ] CLAUDE.md updated if architecture or key design decisions changed
- [ ] `describe()` updated if new field metadata was added

### Test Suite (Catch2, 200+ tests)

Tests live in `tests/`, organized by concern:
- `test_parsing.cpp` — primitives, whitespace, errors, type mismatches, escape sequences
- `test_vectors.cpp` — all vector types, edge cases, element errors
- `test_schema.cpp` — defaults, required, strict mode, marker validation, constraints
- `test_errors.cpp` — `ErrorCollector`, line numbers, `CordException::what()`
- `test_comments.cpp` — line/inline comments, disabled comments, hash in strings
- `test_markers.cpp` — custom delimiters and comment markers
- `test_get_or.cpp` — fallback values, runtime-computed fallbacks
- `test_file_parsing.cpp` — `parseFile()`, `write()`, `writeFile()`, `set()`
- `test_describe.cpp` — `describe()` output, grouping threshold
- `test_custom_struct.cpp` — custom POD types, vectors of custom structs, constraints, defaults
- `compile_fail/` — static_assert tests, verified via CMake `try_compile`

When adding features, add tests. When fixing bugs, add a regression test first.

### Supported Types

**Primitives:** `bool`, `int`, `float`, `double`, `std::string`, and `std::vector<T>` of each.

**Custom structs:** User-defined POD types registered with `CORD_REGISTER_STRUCT(T)`. Can contain primitive fields and vectors of primitives. Nested custom structs not yet supported.

Enforced at compile time via `static_assert` in `schema.add<T>()`, `Value::as<T>()`, `Result::get_or()`, `Result::set()`.

### Key Design Decisions

- `Field::required()` and `Field::default_()` validate eagerly — throw `CordException` immediately if both are set.
- `Value::as<T>()` wraps `std::bad_variant_access` → `CordException` with a clear message.
- `Result::get()` returns `const Value&` (not by value) — don't change this.
- `_tryParseInt`/`_tryParseDouble`/`_tryParseFloat` catch `std::out_of_range` and `std::invalid_argument` explicitly — no `catch (...)`.
- `Result::_values` is `vector<pair<string, Value>>` (not `unordered_map`) — insertion order preserved for `write()` serialization.
- `Result::set()` / `write()` / `writeFile()` enable round-trip editing. `_delimiter` is copied from `Schema` to `Result` at parse time.
- `min()`/`max()` have two overloads: `T val` for numeric fields (value constraint), `size_t count` for string/vector fields (length/element count constraint).
- All public API throws use `std::source_location` as a defaulted parameter — call site file+line in every `CordException`.
- Strict mode off by default. In strict mode: unknown keys AND duplicate keys both produce errors. Comments on by default.
- `min()`/`max()` validate ordering eagerly (min > max throws). `oneOf({})` empty list throws. Same pattern as `required()` + `default_()`.
- Delimiter and comment marker are validated: no empty, no newline, no collision with each other. `schema.add<T>("")` throws — empty key names rejected.

### Known Limitations (out of scope)

No nested sections, no Windows CRLF, no binary formats, comments not preserved on write-back.
